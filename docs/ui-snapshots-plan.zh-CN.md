# 项目页面快照与增量 Preview 改造计划

状态：已实施，纳入 `0.1.8-alpha.1`；`0.1.7` 正式版不包含本次改造。本文记录 2026-09-19 确认的方向；实际验证与限制见末尾。

## 1. 目标

有现有界面时，先确定工单功能落在哪个页面，把该页面及必要的导航、布局搬到 `preview.html` 中，再展示工单改动。用户应能在自己产品的整体视觉中验收，而不是面对孤立的功能 demo。

通过项目内页面快照减少重复读取源码和重建界面的成本。init 建立基线，ticket 复用并局部核对，execute 在真实交付后更新。没有现有界面时才独立设计。

## 2. 固定存放位置与 Git 策略

```text
<用户项目根目录>/
├── .codoop-flow/
│   ├── codoop_flow.toml           # 个人配置，Git 忽略
│   └── ui-snapshots/             # 当前检出版本的页面基线，纳入 Git
│       ├── index.json
│       └── pages/
│           ├── web-orders.html
│           └── web-settings.html
└── docs/tickets/<阶段>/<工单 ID>/
    └── preview.html              # 工单设计记录，沿用现有归档流程
```

- `.codoop-flow/` 属于用户项目，不属于插件安装目录，也不是全局缓存。
- 只忽略配置文件，不能忽略整个 `.codoop-flow/`。
- 配置继续保留文件名 `codoop_flow.toml`；项目路径仍相对于 `target_repo`，不相对于配置所在目录。
- 当前 Runtime 的工单路径固定为 `docs/tickets/`，本次不引入工单路径可配置化。
- 页面基线表示当前分支已实现且经核对的界面，不等于已上线界面。工单 preview 表示计划效果，两者不可混用。

## 3. 配置位置迁移

主要修改：`runtime/codoop-flow/codoop_lib_v1/config.py`、`runtime/codoop-flow/codoop.py` 及调用说明。

- 新项目 setup 默认写入 `<target_repo>/.codoop-flow/codoop_flow.toml`，自动创建父目录；不能写到插件仓库或调用命令的任意工作目录。
- 配置读取优先级：显式 `--config` → 当前目标项目新位置 → 项目根目录旧位置。显式路径无效时直接报错，不偷偷回退。
- 从项目子目录运行时定位 Git 根目录；在项目外运行且没有明确目标时保留明确报错/请求路径行为，不猜其他仓库。
- 新旧文件同时存在时默认使用新位置，报告实际路径；不合并、不覆盖旧文件。
- 已有项目再次 init 时，若只有旧配置，将其完整迁移到新位置，保留设置与未知字段；验证新配置可加载且目标一致后才删除旧文件。失败时保留旧配置。
- 自定义显式配置位置继续受支持，不强制迁移。
- 更新精确的 Git ignore 规则，保留现有个人配置不提交的约定。不要重写其他用户规则。
- 检查所有 `load_config`、`setup_target` 调用及硬编码根目录路径的 skill、脚本、示例和 CLI 帮助，共用同一查找规则。

验收：新项目、旧项目、显式路径、子目录调用和新旧配置并存均能确定性工作；配置移动不改变应用目录和工单目录。

## 4. 页面索引与最小复用规则

建立一份共享快照说明，由 init、ticket、execute 引用，避免三处规则漂移。建议位置：`skills/codoop-init/references/ui-snapshots.md`。

`index.json` 建议采用 `schema_version` 加按稳定页面 ID 索引的 `pages` 对象，每个页面记录：

| 信息 | 用途 |
|---|---|
| 页面名称、所属项目、路由或原生页面入口 | 定位工单目标页面；区分多端同名页面 |
| 项目相对的 HTML 快照路径 | 按需读取单页 |
| 页面源码、公共布局、组件、样式及必要资源路径 | 确定刷新范围 |
| 对上述文件的内容指纹 | 识别提交和未提交改动，避免仅凭 HEAD 判断 |
| 核对时的 Git revision、证据来源及代表性视口 | 追溯上下文；revision 不是唯一有效性依据 |
| 状态及缺失原因 | 区分已核对、待刷新和无法验证 |

- 索引只放简短定位信息，不塞入源码和整页 HTML。
- 按需读取索引及本次页面，不把全部快照注入上下文。
- 共享布局、主题或组件变化时，使依赖它的页面失效；无法确定依赖范围时扩大相关模块检查，不假装缓存有效。
- 页面移动或删除必须核对后更新索引；访问失败不能当作页面已删除。
- HTML 使用模拟数据，保留必要视觉细节，不归档真实个人数据、令牌或登录状态。
- 优先单文件内联所需样式和资源，离线可打开；不引入生产构建或真实 API 依赖。
- 初版不做缓存服务、数据库、后台监听或通用依赖分析框架。确定性的路径/指纹检查如需代码，复用 Runtime 并使用标准库；界面识别与重建由执行 skill 的 agent 完成。

## 5. init：建立与增量刷新页面基线

主要修改：`skills/codoop-init/SKILL.md`。

在配置与项目映射完成后增加页面盘点：

1. 扫描已配置的 web、desktop、mobile 项目；忽略依赖、构建产物和其他项目。
2. 识别已有页面、路由、公共布局、样式和组件，建立页面索引。
3. 首次为已有页面生成代表性 HTML 快照；已有缓存时只重建新增或变化的页面。
4. 能运行时查看真实页面，并打开生成的快照核对布局与视觉。原生页面可以重建为 HTML 视觉表达，但记录来源与表现限制，不声称是原生实现。
5. 无法运行或关键资源缺失时记录无法验证的原因；源码重建稿不能标记为已经视觉核实的基线。
6. 输出新增、刷新、复用、删除和未完成页面的简短统计。

范围：每个实际页面保留代表性内容，不穷举动态路由中的每个数据 ID 或所有交互状态。纯后端或空项目跳过，不能为生成快照而搭建应用。命令行 setup 仍负责确定性配置工作，不宣称仅运行 CLI 就完成视觉扫描。

## 6. ticket：搬入现有页面，再展示改动

主要修改：`skills/codoop-ticket/SKILL.md` 的 Startup、Visual Preview、阶段评审及相关 README。

1. 先确定功能落在哪个现有页面，通过索引定位；没有快照时局部检查源码并补建。
2. 核对页面及相关依赖的内容指纹。有效则复用，无效则刷新本次所需页面。
3. 把现有页面的必要导航、标题、内容区域、相邻模块和设计细节搬进工单 `preview.html`，在副本上加入新功能。
4. 新增页面沿用项目现有公共布局与组件；项目完全没有界面时再依据设计规范独立设计。
5. 只有工单相关的主路径和关键状态需要可交互；背景导航可以仅用于呈现上下文。仍保持单文件、模拟数据、无需登录和真实 API。
6. 生成后实际打开，核对整体视觉、关键交互及适用的窄屏布局；与实际界面不一致的地方明确说明。
7. 在现有 spec 中简短记录所依据的页面和源码版本，便于 execute 识别设计过期；不新增一套重复设计文档。

删除或改写当前“不是 full-product shell”这种容易排除必要页面上下文的表述。限制的是实现无关业务流程，不是保留产品外观。

保持 strict/one_pass 的既有评审规则和 promotion 授权规则。创建、批准或 promote 工单，只归档工单 preview，不以提案覆盖已实现页面基线。保留现有 visual_preview 启用范围，本次不额外扩大 fix 工单的预览要求。

## 7. execute：交付后更新，遵守分支边界

主要修改：`skills/codoop-execute/SKILL.md` 的 Build、Verify、Ship living docs、Finish 说明；核查 `codoop_tools.py` 与 `codoop_lib_v1/ignore.py` 的提交范围。

1. 开发前读取工单 preview、设计依据和当前源码。其他工单已改变页面时，保留有效的新实现，识别本次方案冲突；不能照搬旧 preview 覆盖现状。
2. 完成实现、验证与审查后，以真实交付界面刷新受影响页面，包括没有 preview 的 UI 修复，以及共享样式改动影响的页面。
3. 在工单隔离 worktree 的 `.codoop-flow/ui-snapshots/` 中写入快照和索引，与代码通过既有 finish 提交到工单分支。
4. 扩展现有收尾允许编辑的目录，明确允许快照目录；不因当前 living-docs 仅允许 `docs/prd/`、`docs/tech/` 而漏掉更新。
5. 确认 finish 的生成文件过滤不会丢弃快照，个人配置不会被提交。工作树移除前完成持久化。
6. finish 不自动合并，不能把工单分支快照直接复制回目标仓库主分支。合并时快照随代码进入；并行分支索引冲突按各自页面来源解决，不能整份覆盖。
7. 开发失败、验证未通过时不发布新基线。无法生成/核实快照时保留旧文件并明确标记失效及原因，不能报告快照已同步；在完成报告中列为未完成项。

注意：快照更新是交付资料同步，`ui_capture` 仍是原有真实实现截图检查。HTML 不替代截图，也不能把复制 preview 当作已完成实现核验。

## 8. 文档与完成标准

- `skills/definition-of-done/SKILL.md`：增加受影响页面快照同步或明确缺失状态的检查。
- `README.md`、`README.zh-CN.md`、`docs/install*.md`：更新配置位置、兼容行为与 Git 策略。
- `docs/loop-2-human-centric*.md`、`docs/loop-3-agent-centric*.md`：更新预览生成与交付同步流程。
- 按引用检查 `docs/engineering-design*.md`、配置示例及其余 skills，修正不再成立的路径或流程，不无差别重写文档。
- 实施完成后更新 CHANGELOG；版本号按仓库既有发布流程处理。本计划不发布插件。

## 9. 实施顺序与验收

- [x] 第一步：统一配置定位与兼容迁移，修改共享 Runtime，补充配置回归检查。
- [x] 第二步：确定共享索引格式、快照位置及失效规则，建立最小示例。
- [x] 第三步：更新 init，让已有项目首次建档、再次增量刷新。
- [x] 第四步：更新 ticket，在真实页面上下文生成预览，并实际打开验收。
- [x] 第五步：更新 execute 和完成标准，验证 worktree/finish/分支同步边界。
- [x] 第六步：同步文档，运行相关现有检查及一次完整示例流程。

优先扩展现有 `tests/test_skeleton.py`，不引入新测试框架；实施前阅读其现有配置、setup 和 finish 检查。必要的自动化覆盖：

| 场景 | 预期 |
|---|---|
| 新配置、旧配置迁移、双配置、显式路径、子目录调用 | 正确选择配置，保留设置，项目路径不变 |
| Git 策略 | 配置被忽略，页面快照可提交 |
| 页面未改、局部源码改、共享样式改、未提交改动 | 正确复用或失效，不只比较 commit ID |
| 文件缺失、索引损坏、页面删除 | 不错误复用或误删，提供可恢复路径 |
| 工单仅创建/批准 | 页面基线不包含未实现设计 |
| finish 成功或失败、不同分支 | 快照与对应实现绑定，不提前污染主分支 |

人工视觉验收：选择一个已有导航和列表页的示例项目，init 建档后创建“增加筛选”工单。确认 preview 保留原页面整体视觉并可操作筛选；再次创建同页工单时复用已核实基线；修改共享样式后能触发刷新。再以空项目验证没有界面时的独立设计分支。

## 10. 完成定义

用户在已有项目中看到的是现有页面加本次改动；后续工单无需重复全项目扫描。配置和资料统一放在 `.codoop-flow/`，旧项目仍可使用，未实现提案不会成为当前页面基线，工单分支的快照不会提前覆盖其他分支。


## 11. 本次实施与验证记录

- 配置：共享 Runtime 已实现新位置、旧位置回退、迁移、显式路径和子目录发现；`config-path` 可返回实际路径。相对项目与 worktree 路径锚定目标项目，不受调用目录影响。迁移保留注释和未知表中的同名字段。
- 快照：共享规则位于 `skills/codoop-init/references/ui-snapshots.md`；`codoop.py snapshots fingerprint/check --repo ...` 提供只读文件指纹和有效性检查。页面识别、还原与视觉核对仍由 agent 完成，不是 CLI 自动截图服务。
- 流程：init 建档、ticket 基于已有页面制作提案、execute 在交付分支更新基线；相关文档与完成标准已同步。
- 自动回归：`python3 tests/test_skeleton.py` 全部通过，包括配置兼容、失败迁移、局部/共享样式/未提交改动失效、索引损坏、路径越界、promotion 不替换基线、finish 保留快照且排除个人配置、失败与分支隔离。
- Skill 检查：12 个 skills 均通过 skill-creator 的 `quick_validate`；共享快照引用可解析，`git diff --check` 通过。验证器使用临时目录中的 PyYAML，未新增项目运行依赖。
- 浏览器示例：在独立临时项目中创建原始订单页和对应基线，再在工单 preview 中加入状态筛选。实际对比了原页面、基线与预览；导航、布局和样式一致，筛选从 3 条变为 1 条；检查了 1280px 桌面和 390px 窄屏显示。重复检查可复用，修改主题颜色后基线失效，恢复源码后恢复有效。
- 验证限制：示例经本地 HTTP 服务渲染；浏览器安全策略阻止直接访问 `file://`，所以未声称完成直接离线打开验证。空项目初始化由既有回归覆盖；本次没有对真实业务项目、原生客户端或不同模型的完整自主 skill 执行进行全面验证。
- 版本归属：改造先 stash，发布不含本次改造的 `0.1.7` 正式版后恢复，并纳入 `0.1.8-alpha.1`。不直接修改已安装的插件缓存；临时示例不进入插件仓库。
